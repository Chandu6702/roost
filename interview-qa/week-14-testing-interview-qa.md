# Week 14 — Testing Interview Q&A

## 1. What is the difference between a unit test and an integration test?

A unit test verifies a small piece of behavior in isolation, usually without real infrastructure. An integration test verifies that multiple components work together, often with Spring's application context and real infrastructure such as PostgreSQL.

## 2. What is the Arrange-Act-Assert pattern?

- **Arrange:** prepare inputs, mocks, and test data.
- **Act:** execute the method or operation under test.
- **Assert:** verify the result or observable behavior.

## 3. Why should business logic be unit tested?

Business logic can have many edge cases. Unit tests are fast, isolated, and easy to run repeatedly, so they are useful for calculations, rules, state transitions, and branching behavior.

## 4. What does `@Mock` do in Mockito?

`@Mock` creates a Mockito mock object whose behavior can be controlled and whose interactions can be verified.

## 5. What does `@InjectMocks` do?

`@InjectMocks` creates the class under test and injects the available Mockito mocks into it, typically through the constructor.

## 6. What is the difference between `when(...).thenReturn(...)` and `verify(...)`?

`when(...).thenReturn(...)` defines mock behavior. `verify(...)` checks that an interaction actually occurred.

## 7. Why did we use `thenAnswer(...)` when mocking `save(...)`?

A repository mock does not actually persist an entity. Returning the argument passed to `save(...)` lets the service test continue without a database.

## 8. What is strict stubbing in Mockito?

Strict stubbing helps detect unnecessary or incorrect mock configuration, including stubs that are never used. This keeps tests more precise.

## 9. Why can Mockito matcher usage cause `InvalidUseOfMatchersException`?

Mockito expects argument matching to be used consistently within a mocked invocation. Mixing matchers and raw arguments incorrectly can cause the exception.

## 10. What is `@WebMvcTest`?

`@WebMvcTest` loads the MVC/web layer needed to test controllers without starting the entire application. It is useful for request mapping, validation, JSON mapping, status codes, and controller behavior.

## 11. What is the difference between `@WebMvcTest` and `@SpringBootTest`?

`@WebMvcTest` is a focused MVC slice test. `@SpringBootTest` loads the full Spring Boot application context and is used for broader integration testing.

## 12. Why did we use `@AutoConfigureMockMvc(addFilters = false)`?

The controller test encountered security-filter behavior even though security was not the behavior under test. Disabling filters for that MockMvc test isolates the controller test from authentication/authorization filters without disabling application security globally.

## 13. Why do controller tests matter if service tests already exist?

They verify the HTTP boundary: URL mapping, request binding, validation, status codes, JSON behavior, and controller-level exception handling. A service test does not prove that the REST endpoint is wired correctly.

## 14. What does `@SpringBootTest` provide?

It loads the Spring Boot application context so real components can work together. In our integration test this includes controllers, services, repositories, JPA/Hibernate, Flyway, and PostgreSQL.

## 15. What is Testcontainers?

Testcontainers allows tests to start real external dependencies in disposable containers. Roost uses a PostgreSQL 17 container for integration testing.

## 16. Why use Testcontainers instead of mocking the repository?

A repository mock cannot prove that SQL, Hibernate mappings, Flyway migrations, constraints, transactions, and PostgreSQL-specific behavior work correctly. Testcontainers exercises the real database.

## 17. What is `@DynamicPropertySource` used for?

It registers dynamic Spring properties at test startup. With Testcontainers, it supplies the JDBC URL, username, and password generated by the PostgreSQL container.

## 18. Why did we use `RANDOM_PORT`?

`RANDOM_PORT` starts the embedded web server on an available port, avoiding assumptions about port 8080 and allowing the test to make real HTTP requests.

## 19. Why use `TestRestTemplate` in this integration test?

It lets the test communicate with the running Spring Boot application through HTTP, exercising the real controller → service → repository → database path.

## 20. What does the Roost POST → GET integration test prove?

It proves that data can travel through the real application, be persisted in PostgreSQL, and be retrieved through a later HTTP request. It verifies real integration rather than mocked interactions.

## 21. Why did we use `ResponseEntity<String>` for the monitor GET?

The response contained `Page<ProbeResultResponse>`, and directly deserializing that abstraction caused a Jackson deserialization problem in the test. Reading the actual response as a `String` let us verify the HTTP/persistence behavior without changing the production DTO solely for the test.

## 22. What is a concurrency test?

A concurrency test verifies behavior when multiple operations happen concurrently or overlap. Our test sends 20 concurrent probe-result POST requests to the same monitor.

## 23. Why did we use `CountDownLatch`?

It coordinates the worker threads. One latch waits until all workers are ready; another releases them together so the requests begin concurrently rather than merely sequentially.

## 24. What does `ExecutorService` provide?

It manages a pool of worker threads and allows the test to submit tasks for concurrent execution.

## 25. What does our concurrency test actually prove?

It demonstrates that 20 concurrent probe-write requests completed successfully and that all 20 probe results and 20 corresponding audit records were persisted for the monitor.

## 26. Is the concurrency test an idempotency test?

No. Idempotency requires a way to identify duplicate requests, such as a client-generated request ID backed by a uniqueness constraint. Our test sends 20 distinct legitimate probe results and expects 20 rows.

## 27. Does the concurrency test prove there are no lost updates?

Not literally. The test performs concurrent inserts, not concurrent updates to the same database row. A more precise description is that it tests for lost probe writes under concurrent POST requests.

## 28. Should every Spring Boot method have all these test types?

No. Use the smallest test that can effectively prove the behavior. Pure calculations can use unit tests, service logic can use Mockito, controllers can use `@WebMvcTest`, persistence can use integration tests, and concurrency-sensitive behavior can use targeted concurrency tests.

## 29. Which testing skills should a Spring Boot developer prioritize?

Prioritize JUnit 5 fundamentals, Mockito service testing, controller slice testing, full integration testing, and Testcontainers. Understand concurrency testing conceptually and use it where the application has a real concurrency risk.

## 30. What is the main testing lesson from Week 14?

Testing is about choosing the right boundary between isolation and realism. A strong test suite combines fast isolated tests with targeted integration tests rather than relying exclusively on either mocks or full end-to-end tests.
